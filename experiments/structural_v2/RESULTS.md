**変更内容と棄却理由**

- **7 枚の core**: `STRUCT_BACKING=7` と候補幅の変更。six-case 比較は平均で約 218–260 手悪化した。名称の数字は `SEVEN_WIDTH` 設定値であり、実際の `CHOSEN W` は seven42 が全件 43、seven44 が 44–45、seven46 が 45–46、seven48 が 45–47。seven46/48 は同時に測定した baseline がなく、異なるケース数の平均と直接比較しない。
- **三商品で主紙を共有**: 二つのペアを三商品共有＋単独商品へ組み替える候補を探索。全 6 件で `feasible=0, accepted=0`。候補組の試行数は各 2346 または 2415、アンカー条件を満たす候補は各 5679–6211 あったが、三商品の literal core goal を同時に確保できなかった。今回の変換で得られなかったという結果であり、三商品共有一般の不可能性を証明するものではない。
- **局所的な core / ペア同時探索**: `joint` は全 6 件で `changed_columns=0, changed_pairs=0`、出力設計も baseline と一致し、手数も一致。例えば seed 0000 は修復 73 回中 72 回が失敗。`accepted` が正でも最終採用設計が変化したとは限らない。ペアのみの `pairs` は seed 0002 で `changed_pairs=2`、ほかでは 0 だが、行の再構成等も含め出力設計は全件異なり、平均では悪化した。
- **全商品からの大域的再ペアリング**: 全商品対の literal goal feasibility を求め、matching と Hungarian 割当で固定アンカーを満たす主紙を再構成。`global` は全 4 件で core を 1–2 列、42–56 ペア変更した。`balanced` も 1–2 列、46–57 ペア変更。構造変更は実現したが、平均はそれぞれ +99.5 / +150.25 手。`CORE_JOINT_RETURN_MUTATED=1` で変更済み候補を試す探索なので、元設計より評価が悪い候補も強制的に返している。変更できたことと改善できたことを区別する。
- **合成注文での実測による設計選択**: `measured` / `measured_pairs` は proxy のみでなくルータの合成注文評価で候補を選択。実際の出力設計差は前者が seed 0001、後者が 0002/0003。後者の平均 −0.333 手は 6 件合計でわずか −2 手で、平均 CPU は 2 秒を超えた。改善の再現性も時間適合も示しておらず、不採用。
- **core の担当列を 1 列拡大**: `widen` は合成評価で改善候補なし（全件 `improved=0`）。`CORE_WIDEN_FORCE=1` により実現可能な変更を返した結果、5 件は幅が 1 増加、seed 0004 は実現可能候補なし。平均 +114 手、最大 wall 2.401 秒。強制変更の性能確認であり、通常選択が改善を採用した結果ではない。
- **1 手先の rollout**: 近い評価の候補状態から、同じ一様サンプル次注文を簡易ルータで処理して順位を付ける。サンプルは実際の未来の注文を参照しない。候補変更は rollout4 で 1 ケースあたり 91–132 回、rollout16 で 132–176 回発生したが、全体では悪化。初期設計が一致した seed 0000/0001/0003/0004 だけでも差の平均は +18.0 / +19.75 手であり、設計差を除いても改善の証拠はない。ただしこの部分集合も独立検証ではなく、時間打ち切り差が残る。
- **Arbitrary core**: 完全グラフの比較用 witness を保持する制約を外せる設計探索と、実際の可視性から遷移を構成するルータを実装。今回の全 4 件では各 1 列、40–53 ペアを変更したが平均 +76.5 手。全ログに `CUSTOM_CORE_GRAPH` がなく、最終選択設計には依然として全ペアの witness が残った。したがって、一般化した可視性ルータの性能や動作をこの結果で検証できたとは言えない。
- **Suffix の穴を増やす**: 所有商品の core goal を維持しつつ、ペア共有主紙の suffix 共通セルを穴へ変更して他商品から借りやすくする探索。各 1652–1823 候補、222–464 件の実現可能な変更を調べたが、全件 `edits=0, foreign=0, own=0`。この評価関数で採用できる変更がなかった。
- **Core の相対価値反復**: `CORE_VALUE_ITER=12`。各商品への最短経路に限定し、その終端状態の将来価値を反復計算して core の経路選択へ用いる。全件で期限内に 5–7 sweep で収束し、`E=0`、最大 20 手/注文。追加計算の CPU は B=5 で 2.389–2.782 ms、B=6 で 15.236–16.730 ms。計算量は小さいが、全 6 件平均は +37.5 手、初期設計が同じ 5 件でも +4.2 手で、不採用。
- **実効 16 サンプルの rollout 追試**: `rollout_wide.cpp` はサンプル上限と配列を 32 へ拡張し、default 4 を保持した別ソース。`ROLLOUT_SAMPLES=16, ROLLOUT_CPU=2.0` を指定し、baseline / variant とも route 系の時間枠を 6.0（Linux 3.6 秒）へ延長した。全 6 件で初期設計が一致し、全 1024 注文を処理、全件 `E=0`。rollout は近接候補のある 974–997 注文で動作し、`trials=32×calls`（2 候補 × 16 サンプル）、`aborted=0` で完了した。追加探索 CPU は 0.484–0.669 秒。差は seed 順に +11 / +82 / −2 / +1 / −7 / +50 手、平均 +22.5 手で、最大 wall も 2.233 秒。不採用。

**見かけの改善・設定名に関する注意**

※ `triple` の −55.333 手を方式の成果として数えてはいけない。先頭 192 行は seed 0000–0004 で同一、手数も完全一致。seed 0005 のみ baseline が `CHOSEN W=39`・10936 手、triple が `W=36`・10604 手となり、6 件の差の合計 −332 手をすべて説明する。三商品共有の採用は全件 0。探索時間・打ち切り条件による設計差を含む比較である。

`rollout16` は JSON で `ROLLOUT_SAMPLES=16` を指定しているが、当該 `rollout.cpp` は `clamp(..., 2, 4)` と `array<int,4>` を使用する。実効サンプル数は 4 で、ログも `trials=8×calls`（候補 2 状態 × 4 サンプル）と一致する。rollout4 との主要な設定差は `ROLLOUT_CPU=.4`（通常 .2）であり、Linux では探索 CPU 予算 .24 秒（通常 .12 秒）。16 サンプルの比較実験として解釈しない。

rollout の初期設計が baseline と異なるケースは rollout4 の seed 0002/0005、rollout16 の seed 0002。初期設計が同じケースでも `synthetic_queries` や後半の `trace_skips` が異なる場合があり、同一設計だけで完全に同条件にはならない。

※※ `suffix` の −10.667 手も方式の改善に数えない。全件 `edits=0` で、seed 0004 以外は設計・手数とも baseline と同一。seed 0004 は双方 `CHOSEN W=37` だが先頭 192 行が異なり、10645→10581 手（−64 手）が平均差のすべてを説明する。合成評価回数は baseline 445 / suffix 1806、`trace_skips` は 48 / 0 と、時間枠による違いもある。

`core_value` は seed 0002 で baseline が `W=36, index=0`、variant が `W=36, index=4` と初期設計が異なり、10653→10857 手（+204 手）。同じ幅でも同じ設計とは限らない。他の 5 件は設計が一致し、差は順に +13 / +8 / +2 / +1 / −3 手（合計 +21、平均 +4.2）。全件の +37.5 手を価値反復単独の効果とは解釈しないが、同一設計の結果にも改善の証拠はない。
